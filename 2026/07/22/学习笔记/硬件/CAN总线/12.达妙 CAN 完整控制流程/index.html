初始化阶段

程序启动后不应立即发送力矩，而要完成：

  1. 打开 USB2CAN；
  2. 设置与电机一致的波特率；
  3. 设置标准帧和接收过滤规则；
  4. 确认 CAN_ID、Master ID 和控制模式；
  5. 确认 PMAX、VMAX、TMAX 等映射范围；
  6. 等待并验证电机反馈；
  7. 检查错误码、温度和机械状态。

只有通信和状态正常后才进入使能流程。

使能与反馈确认

MIT 模式使能报文为：

发送成功后不能立即假定电机已使能，而应等待对应反馈，检查：

  • CAN 帧 ID 是否符合反馈规则；
  • DATA 中的 Motor ID 是否正确；
  • 状态是否进入使能；
  • 是否存在过压、过流、过温或通信错误。

使能确认超时应停止后续控制。

外部控制器与 MIT 增益

如果电脑自己运行 PD 控制：

$$
\tau_{cmd}=K_{p,c}(q_{des}-q)-K_{d,c}\dot q
$$

这里的 $K_{p,c}$ 和 $K_{d,c}$ 是电脑端控制算法参数。

MIT 帧中的 Kp 和 Kd 则是驱动器内部 MIT 控制参数，两组参数不应混为一谈。

安全限制

真实电机控制至少需要检查：

  • 力矩上限；
  • 位置软限位；
  • 速度上限；
  • MOS 与电机温度；
  • 驱动器错误码；
  • 反馈超时；
  • 控制周期异常；
  • USB2CAN 断开或发送失败。

通信看门狗

如果程序崩溃、USB 断开或 CAN 线脱落，电机不能无限保持最后一个危险命令。

应结合驱动器提供的 CAN Timeout 或看门狗功能，同时在电脑端记录最后反馈时间：

硬件急停、驱动器超时保护和软件检查应相互补充，不能只依赖异常处理代码。

控制频率和 CAN 波特率

1 kHz 控制表示程序每 1 ms 更新一次控制量；1 Mbps CAN 表示总线每秒传输约一百万 bit。二者不是同一个概念。

PC、普通操作系统、Python 和 USB2CAN 都可能引入延迟与抖动。sleep(0.001) 不保证每次都严格间隔 1.000 ms。

实验时应测量：

  • 实际控制周期；
  • 周期抖动；
  • 报文往返延迟；
  • 丢帧与超时次数；
  • 多电机情况下的总线占用率。

对实时性要求更高时，还需要考虑实时 Linux、MCU、实时控制器或其他工业总线方案。

安全退出

控制结束时，不应让程序直接消失。合理流程为：

正常结束、用户按下 Ctrl+C、程序抛出异常或安全检查失败，都应进入统一的退出路径。

异常情况下软件命令未必还能成功发送，因此实际机器人仍需要独立急停和硬件安全措施。

完整流程

完成这一流程后，CAN 不再只是几组十六进制数据，而是成为从控制算法到真实电机、再从传感反馈回到控制器的完整闭环通道。
