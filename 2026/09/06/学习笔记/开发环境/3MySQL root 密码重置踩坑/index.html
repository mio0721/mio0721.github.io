MySQL root 密码重置踩坑

发表于2026-09-06|更新于2026-09-06|学习笔记开发环境
|浏览量:

MySQL root 密码重置踩坑：密码末尾的单引号让我排查了半天

最近在 Windows 上安装 MySQL 9.7，MySQL Server 本身安装得很顺利：

MySQL Server 9.7.2
Port: 3306
Service: MySQL97

安装日志里也明确出现了：

ready for connections

说明数据库服务已经正常启动。

但真正登录时却一直报：

ERROR 1045 (28000): Access denied for user ‘root‘@’localhost’
(using password: YES)

一开始一直以为是 MySQL 服务、数据目录、权限或者认证方式出了问题。

最后发现，真正让我踩坑的是一个非常不起眼的东西：

我的 root 密码末尾本身就包含一个 ASCII 单引号 ‘。

而单引号在 SQL 中又恰好用于表示字符串。

  1. 最开始的现象

使用 PowerShell 登录 MySQL：

& “E:\Programs\MySQL\MySQL Server 9.7\bin\mysql.exe” -u root -p

输入密码后：

ERROR 1045 (28000): Access denied for user ‘root‘@’localhost’
(using password: YES)

这里其实可以先判断出几件事：

mysql.exe 可以正常运行 ✓
MySQL Server 可以连接 ✓
3306 端口正常 ✓
root 用户存在 ✓
密码认证失败 ✗

也就是说，问题已经不是：

MySQL 有没有启动

而是：

root 的密码为什么认证失败

  1. 我的密码末尾包含单引号

假设密码是：

mioSQL’

最后这个字符：

‘

就是普通键盘上的 ASCII 单引号。

它本身作为 MySQL 密码完全没有问题。

例如在登录界面：

Enter password:

此时直接输入：

mioSQL’

就可以。

问题出现在后来为了重置 root 密码，需要写 SQL：

ALTER USER ‘root‘@’localhost’ IDENTIFIED BY ‘密码’;

这时候，密码里的 ‘ 和 SQL 本身用于包围字符串的 ‘ 撞在了一起。

  1. SQL 中的单引号不仅仅是普通字符

比如一个普通密码：

mioSQL

对应 SQL：

ALTER USER ‘root‘@’localhost’
IDENTIFIED BY ‘mioSQL’;

其中：

‘mioSQL’

两边的单引号不是密码的一部分。

它们的作用是告诉 SQL：

这里是一段字符串。

结构实际上是：

‘ mioSQL ‘
↑ ↑
字符串开始 字符串结束

  1. 密码本身也有 ‘ 时就麻烦了

假设真正密码是：

mioSQL’

如果直接写：

ALTER USER ‘root‘@’localhost’
IDENTIFIED BY ‘mioSQL’’;

看起来似乎只是：

密码 mioSQL’
+
外面的结束单引号

但 SQL 字符串并不是这么解析的。

在 SQL 中，如果字符串内部本身需要包含单引号，需要使用：

‘’

两个连续单引号表示字符串内容中的一个：

‘

因此真正正确的写法是：

ALTER USER ‘root‘@’localhost’
IDENTIFIED BY ‘mioSQL’’’;

注意最后：

‘mioSQL’’’
^^^

这里连续出现了三个 ‘。

  1. 为什么最后需要三个单引号

可以拆开来看。

目标密码：

mioSQL’

SQL 字符串开头：

‘

普通内容：

mioSQL

密码里的一个单引号需要写成：

‘’

最后还需要一个单引号结束 SQL 字符串：

‘

所以：

字符串开始 密码内容 密码里的 ‘ 字符串结束
‘ mioSQL ‘’ ‘

组合起来：

‘mioSQL’’’

因此：

ALTER USER ‘root‘@’localhost’
IDENTIFIED BY ‘mioSQL’’’;

最终 MySQL 得到的密码才是：

mioSQL’

而不是：

mioSQL

或者一条语法错误的 SQL。

  1. 登录时却不需要转义

这里特别容易混淆。

如果执行：

& “E:\Programs\MySQL\MySQL Server 9.7\bin\mysql.exe” -u root -p

出现：

Enter password:

这里输入的是密码本身，不是 SQL。

所以密码如果是：

mioSQL’

就直接输入：

mioSQL’

不需要写成：

mioSQL’’

更不需要写：

‘mioSQL’’’

可以这样理解：

密码输入框
→ 输入真实密码

SQL
→ 输入一段描述密码的 SQL 字符串
→ 特殊字符需要遵守 SQL 字符串语法

  1. 最后选择直接换一个密码

排查清楚以后，我没有继续使用这个带单引号的密码，而是直接换成了一个不包含 ‘ 的新密码。

然后重新执行：

ALTER USER ‘root‘@’localhost’
IDENTIFIED BY ‘新的密码’;

之后再次登录：

& “E:\Programs\MySQL\MySQL Server 9.7\bin\mysql.exe” -u root -p

成功：

Welcome to the MySQL monitor.
Commands end with ; or \g.

mysql>

执行：

SHOW DATABASES;

返回：

+——————–+
| Database |
+——————–+
| information_schema |
| mysql |
| performance_schema |
| sys |
+——————–+

到这里可以确认：

MySQL Server ✓
root 用户 ✓
root 新密码 ✓
3306 ✓
SQL 查询 ✓

问题解决。

  1. 为什么这个问题很容易误导排查方向

这个问题麻烦的地方在于，表面现象只是：

ERROR 1045

于是很容易开始怀疑：

MySQL 服务没有启动？
3306 端口有问题？
Windows 防火墙？
root 用户权限？
authentication plugin？
my.ini 配置？
datadir 配错了？
Windows Service 权限？

实际上 MySQL Server 从一开始就是正常的。

安装日志已经给出了很重要的信息：

ready for connections

而登录时出现的是：

Access denied

这两个信息组合起来，实际上已经说明：

服务器已经正常运行
↓
客户端已经找到服务器
↓
连接过程正常
↓
失败发生在身份认证阶段

所以遇到 ERROR 1045 时，应该优先检查：

用户名
↓
密码
↓
特殊字符
↓
host
↓
认证方式

而不是第一时间去折腾服务器安装。

  1. 顺手踩到的 PowerShell 小坑

另外还有一个和 MySQL 本身无关的小坑。

一开始我在 PowerShell 中写：

“E:\Programs\MySQL\MySQL Server 9.7\bin\mysql.exe” -u root -p

结果报：

表达式或语句中包含意外的标记“-u”

这是因为 PowerShell 会把：

“E:\Programs\MySQL\MySQL Server 9.7\bin\mysql.exe”

先当成一个普通字符串。

如果要执行一个带空格路径的程序，需要加 PowerShell 的调用运算符：

&

因此正确写法是：

& “E:\Programs\MySQL\MySQL Server 9.7\bin\mysql.exe” -u root -p

这和 MySQL 没有关系，是 PowerShell 自己的语法。

  1. 一个值得记住的规律：数据和代码不是一回事

这次的问题其实不只存在于 MySQL。

很多编程语言都有类似情况。

例如真实字符串：

I’m Mio

如果放到某种使用单引号表示字符串的语言中：

‘I’m Mio’

就可能出现歧义。

因此需要：

转义

本质上是因为：

某些字符既可以作为“数据”，又可以作为“语法”。

常见的特殊字符包括：

‘
“

`
$
%
_

不同环境中的处理规则又不一样。

例如：

SQL
Python
C++
PowerShell
Bash
JSON
YAML
正则表达式

都有自己的转义规则。

所以以后看到：

密码明明没输错
路径明明没写错
字符串看起来也一样

但程序就是报错时，可以检查：

里面是不是包含了当前语言有特殊含义的字符。

  1. 开发环境密码的一个实际建议

并不是说密码中不能出现单引号。

MySQL 完全支持：

‘

真正的问题是：

它会增加 Shell、SQL、配置文件、Docker Compose、环境变量等场景下的转义复杂度。

例如以后可能需要把数据库密码写进：

.env
docker-compose.yml
Python
SQL
Shell
CI/CD

不同环境对：

‘
“
$
\

的解释可能不同。

因此在个人开发环境中，可以优先选择：

大小写字母
数字
@

_

这种不容易和常见配置语法冲突的组合。

正式生产环境则应使用足够随机和高强度的密码，并通过：

环境变量
Secret Manager
Docker Secret
Kubernetes Secret

等方式管理，而不是为了省事降低密码强度。

  1. ERROR 1045 的快速排查思路

以后再遇到：

ERROR 1045 (28000):
Access denied for user …

可以按照这个顺序排查：

ERROR 1045
↓
MySQL Server 是否 Running？
↓
能否连接到 3306？
↓
用户名是否正确？
↓
host 是否正确？
root@localhost
↓
密码是否正确？
↓
密码是否包含特殊字符？
↓
如果通过 SQL 修改密码
是否正确进行了字符串转义？
↓
再检查用户权限和认证方式

这样比一上来就重装 MySQL 高效得多。

本文小结

这次最值得记录的并不是怎么重置 MySQL 密码，而是这个很小却很典型的坑：

密码：

mioSQL’
↑
ASCII 单引号

作为密码输入时：

mioSQL’

直接输入即可。

但是如果把它写进 SQL：

ALTER USER ‘root‘@’localhost’
IDENTIFIED BY ‘…’;

因为 ‘ 本身又是 SQL 字符串定界符，所以密码中的 ‘ 必须写成：

‘’

因此密码：

mioSQL’

对应 SQL：

ALTER USER ‘root‘@’localhost’
IDENTIFIED BY ‘mioSQL’’’;

最核心的一句话就是：

一个字符作为“密码数据”没有问题，不代表它放进 SQL 源码后仍然可以原样书写。

这次 ERROR 1045 最终并不是 MySQL Server、端口、数据目录或者 Windows Service 出了问题，而是密码中的特殊字符和 SQL 字符串语法混在了一起。

以后遇到类似问题，除了检查“值对不对”，还要检查：

这个值放进当前语言以后，是数据，还是被当成了语法。
